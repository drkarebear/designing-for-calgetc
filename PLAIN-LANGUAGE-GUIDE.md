# Plain-Language Guide for Designing for Cal-GETC

The site's job is to make Cal-GETC easier to use, not to reproduce the standards manual in a prettier layout.

## First-read rule

A faculty member should be able to answer these four questions quickly:

1. **What is required?**
2. **Does my course fit?**
3. **Where should the COR show it?**
4. **What do I do next?**

Put nuance, version history, acronym explanations, and unusual edge cases behind progressive disclosure when possible.

## Copy rules

- Prefer one idea per sentence.
- Prefer direct verbs: **show, check, choose, open, confirm**.
- Aim for paragraphs under about 35 words.
- Use bullets for criteria and comparisons.
- Do not explain the same caveat on every page when a short label will do.
- Keep official terminology when it matters, then translate it once.
- Do not turn faculty-facing guidance into legal or bureaucratic prose.
- Use **Watch for this** instead of **Gray area / useful nuance**.
- Use **Does this course fit?** instead of **Does this course sound like a fit?**
- Use **Show it in the COR** instead of **Make it visible in the COR**.
- Keep version history and acronym maps available, but secondary to the task.
- Never simplify by changing the substance of an official requirement.

## Useful content hierarchy

**Need to know now**
- requirement
- units/course count
- fit / not-fit cues
- COR evidence
- next action

**Useful when needed**
- reviewer rationale
- version changes
- CCN/C-ID/TCA distinctions
- exceptions and edge cases
- technical privacy/accessibility details
